Gemini Decisions API 
Google join Jev and OpenAI in the decision model category with "Gemini Decision 1". This new model API is almost identical to Jev: it supports the same three types of questions (yes/no, choice, and rubric-scoring) and even reuses Jev's term "Noul" for a yes/no question. 

It's priced the same as the GPT-6 Luna decision model: 10 cents per million input tokens, and output is free. Jev remains the cheapest of the three, at 4.2 cents per million. 

Jev is text (and JSON) only. OpenAI can handle text and images. Gemini Decision 1 is fully multi-model: it covers text, images, audio, video, and PDFs. 

I tested it against video by passing these questions to it along with my Yonkers stomping robot video file: 

dragon: Does this video have a dragon in it?
robot: Does this video have a robot in it?
france: Is this video set in France?
usa: Is this video set in the USA?

Jev and OpenAI both return 1.0 or 0.0 for yes/no questions, but Gemini insists on being a little less confident than that:

aws-emulator 
Finally, an official emulator from AWS to run tests against a local clone of their many different services without having to provision a paid API key to do so. 

It's written in Rust by a huge swarm of agents - 29,684 commits in the first three weeks of the project. Swaminathan (Swami) Sivasubramanian wrote about how it came to be in a guest post on Werner Vogels' blog. 

It currently requires Docker to run on macOS or Windows. I'm hoping they fix that in the future - it would be great if you could download a single binary and use that as part of a standard test suite in other languages and on other platforms.

AWS Emulator README 

AWS Emulator is a local emulator of the AWS APIs. You use it to test your software without calling AWS, on your own machine, on a development server, or in continuous integration (CI). You don’t need an AWS account. Your requests go to the emulator, not to AWS. So you work with emulated resources instead of AWS resources. AWS Emulator has no additional service fee. You pay only for AWS resources when you deploy on AWS. 

The emulator is a local program that serves an AWS API endpoint. It has no graphical interface. After you start the emulator, you set environment variables to point the AWS CLI or an AWS SDK at its endpoint. Then you run your code as usual. In embedded mode, you pass the emulator’s HTTP client to your SDK instead. 

AWS Emulator is for building and testing. Don’t use it for production workloads or to test security. See Security in AWS Emulator .

Release: llm 0.37.2 

Fixes a security issue reported by Daniel de Araujo in GHSA-v9h7-jj4g-f862 and GHSA-r639-rr7r-x72w . 

LLM has a mechanism called extra-openai-models.yaml - now managed by the new-in-0.37 llm openai endpoint add command - for using LLM with OpenAI-compatible API endpoints from other providers. 

Daniel reported two ways this could accidentally send your configured OpenAI API key to one of those providers: if the key named by api_key_name had never been stored, or if a responses: true model was run with -o chat_completions 1 .

Anthropic's IPO roadshow video 
Anthropic kicked off their IPO roadshow yesterday, and their roadshow video has some previously unreleased information about how their business works. 

The section on "Approach to compute" with co-founder Tom Brown is particularly interesting, describing how Anthropic train and serve Claude across AWS Trainium, Google TPUs, NVIDIA GPUs, and AMD GPUs. 

I'm not sure why there's no official video transcript, but here's one that I extracted using MacWhisper. Highlights below: 

We train and serve Claude now across all four major chip families. That's only possible because early on we made an unconventional bet on a multi-chip strategy. At the time, many people thought that running AI models on different chips wasn't worth the effort. Each chip needs its own tailored software stack and inference stack, which is expensive and difficult to build. We've now been doing it for years, and we've gotten incredibly good at it. [...] 

As an example, this year, we started working with AMD GPUs for the first time. In the past, bringing on a new chip platform took dozens of engineers months of work This time, we had Mythos try it out. It got Claude running on AMD in just three days, with basically no human intervention . Claude ported or wrote almost 100% of the kernels. [...] 

The second driver of our compute advantage is our rate of discovery of compute multipliers. We focus on total effective compute, which is the multiplicative product of physical capacity times the compute multipliers that we discover. Each one we discover makes our pool of total effective compute bigger. For example, say you need 100 units of compute to train a model of a certain intelligence. A 4x compute multiplier means you can use 25 units of compute to train the exact same model. Or you can use those hundred physical units to train an even more intelligent model that would have previously required 400 units. 

Compute multipliers create a competitive advantage for us that's hard to replicate. They build on each other. Each new multiplier we discover has a positive effect on the multipliers before it. They stack. We believe that this can accelerate even further as we approach recursive self-improvement. Claude will be able to discover compute multipliers entirely by itself , allowing the number of compute multipliers to grow faster and faster. 

We got a hint at Anthropic's multi-chip strategy last September in their postmortem of three recent issues , where they described bugs that affected just their TPU deployments.

Faster Retrieval for Better, More Efficient RAG 

Maximum inner product search (MIPS) sits at the core of recommendation systems, search, and retrieval-augmented generation (RAG). Given a query vector, MIPS systems search within a database of millions of candidate key vectors for the one that best matches the query. The original data point associated with that best-matching key is then used to handle the query: in RAG, the document that is best suited to answer the question is typically prefixed to the query. 

As the number of keys grows to millions and vector dimensions reach thousands, the computational cost of running an exhaustive comparison of the query to all keys grows dramatically. Numerous approximate methods have been proposed to trade off accuracy for speed using clustering and quantization. While these baseline methods focus on the properties of the set of keys to build up clever indexing structures, their geometric arguments loosely assume that the set of queries itself will resemble that found in keys, or bypass any considerations about what the queries will look like. This can be problematic on two fronts: In the crucial RAG case, queries arise from short user-generated questions, whereas keys represent long, informative, and curated pieces of text, making keys and queries substantially different. Additionally, most MIPS use cases deployed in production target an existing base of users with a stable, well-characterized query distribution — a signal that generic, query-agnostic methods leave untapped. Crafting methods that work best for a likely source of inputs — rather than aiming for good performance on all possible inputs — is a central tenet of modern machine learning that helps redirect compute resources more efficiently. 

In Amortizing Maximum Inner Product Search with Learned Support Functions , a paper presented at ICML 2026, researchers from Apple train small neural networks (NNs) — once, offline, for a fixed database of keys — that learn how to route queries toward their best match faster. Their approach trades off an upfront amortization cost to understand how typical queries tend to be matched in exchange for faster, more accurate retrieval at inference time through these small NNs. 

The Basics of Maximum Inner Product Search 

A fundamental principle in MIPS is to leverage the geometry of the set of keys to speed up search: Typical MIPS systems split the set of keys into k clusters — k is typically much smaller than the total number of keys n — keeping track of a representative centroid for each cluster. When receiving a new query, the system compares it with these k centroids. The query is then routed toward the cluster of the representative centroid it is closest to, and subsequently compared exhaustively with all keys stored in that cluster. If the database has n keys and k evenly distributed clusters, the effective number of keys that will be considered in that second step is on the order of n / k — a factor-of- k speedup when compared to the n comparisons done in the naive exhaustive approach. EventSourcingDB 1.3.0 is Available 

EventSourcingDB 1.3.0 is out, and it is faster and more stable than any version before it. Writing and EventQL queries are considerably faster, reading is faster as well, every request is bounded in time, and more than sixty fixes went in. Next to all that, it brings a new API that reports the outcome of every request it accepts in its body and names every error with a code of its own.

This post walks through what changed and what to mind when you upgrade. The v1 API is supported until January 31, 2027 , and a later release removes it, so you can move to the new one at your own pace. And from today on, the documentation of EventSourcingDB lives on eventfoundation.io ; every old link leads there. 

A New API, Built to Last # 

The new v2 API runs next to the v1 API, on the same data. Its central idea is simple: once the server has accepted a request, its outcome is in the body . A request counts as accepted when it is authenticated, its body has the shape its route expects, and it stays within its limits. A precondition that does not hold, an event type that is not known, a database in read-only mode – all of these come back as an answer the client can read, rather than as a status code it has to interpret. 

Every error carries a code that is a link to its own page , which explains why it happens and how to fix it. You will find them all under Errors . Streamed answers that come to an end, such as reading events, close with an explicit end item, so a client can tell a complete answer from one that was cut off. While a stream waits, the server sends heartbeats through it, which keeps a proxy from closing it in between. 

The v2 API also brings recursive preconditions : isSubjectPristine , isSubjectPopulated , and isSubjectOnEventId can now apply to a subject together with every subject below it. That is useful whenever a decision depends on a whole part of the tree rather than a single subject. 

The current versions of all eight client SDKs speak both APIs and use the v2 API wherever the server offers it. So apart from updating your SDK, you do not have to change your code, as long as a proxy in front of the database lets through the HTTP method QUERY , which the v2 API uses for reading. If you call the HTTP API directly, Migrating to v2 shows what changes, route by route. 

Moving and Backing Up Data # 

Exporting and importing make it easier to move events into a new database. Both work with one plain CloudEvent per line, including its ID and time, so an export imports without any conversion . Since the import computes the hashes itself, you can also export a history, remove personal data from it, and import the result without having to compute any hash by hand. 

Incremental backups hold only the events written since a previous backup. A restore takes a full backup followed by its increments, which keeps regular backups of a large database small. Restoring itself has become considerably faster too, since it now writes events in batches.
