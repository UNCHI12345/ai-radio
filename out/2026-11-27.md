sqlite3_rsync: Database Remote-Copy Tool For SQLite 
This additional SQLite tool has been around for a while now - it was added as "experimental" in SQLite 3.47.0 in October 2024 and enhanced in SQLite 3.50.0 in May 2025 . It was only today that I understood one of its most attractive characteristics. 

Normally, if you want to grab a snapshot copy of a SQLite database, you need to use either the backup API or VACUUM INTO . In both cases you need enough disk space to create a duplicate copy of your database, so if you're on a small instance and you already use more than half of the available disk you are plain out of luck. 

sqlite3_rsync can copy a snapshot of your database over an SSH connection to another machine, without first needing to create a full local copy! 

It's also good for synchronizing an existing copy of a database without re-transmitting the entire thing over the network. It works in a similar way to regular rsync: 

The core idea behind the protocol is that the replica sends cryptographic hashes for pages or groups of pages over to the origin side. The origin sends back page content that differs, or requests finer-grain hashes if a multi-page hash does not match. If the origin and replica start out being vastly different, the total network bandwidth can exceed the size of the entire database, due to the overhead of exchanging hashes, but the excess bandwidth is not great - a few percent at most.

datasette-charts 

Suggests charts for any Datasette table, view or SQL query, and lets you build your own. 

Installation 

Install this plugin in the same environment as Datasette. 

datasette install datasette-charts 

Screenshot 

Usage 

Every table, view and SQL query page gets a Suggested charts panel at the top. It shows a row of charts, best first, each with a thumbnail, a title and the reason it was suggested. Select one to see it at full size. 

Beside the full-size chart is a builder for changing the chart type, columns, aggregates, time units and bins. "Build a chart" at the end of the row starts from scratch. Anything the plugin can suggest can be built by hand. 

The chart you are looking at is kept in the page's URL fragment, so the address bar always holds a link to it. 

Charts never fetch every row. Each one compiles to a SQL query that returns a small, aggregated result, available through the "This chart's SQL" link.

The llama.cpp × AMD Benchmark dashboard is available on Hugging Face. It lets you track prompt processing and text generation performance across llama.cpp builds, models, and quantizations, so you can explore how local inference performs on AMD Ryzen and Radeon hardware. 

Local inference performance changes as models, kernels, and builds evolve. We want those changes to be easy to inspect for any AMD developer: pick a hardware, a model and a build, compare quantizations, and follow performance over time. The benchmark workflow and underlying results are public, so you can also inspect how we benchmark inference performance. 

Quick start

You can choose Hardware , Model , and llama.cpp build in the Configuration sidebar. The current hardware choices are Radeon 8060S (gfx1151) and Radeon AI Pro R9700S (gfx1201). 

In the Overview tab, compare quantizations for one hardware, model, and build. The two charts show PP512 (512 input tokens, no generation) and TG128 (128 generated tokens), both starting at context depth zero. 

In the Build history tab, track PP512 and TG128 across all recorded builds for the selected hardware, model, and quantization. 

In the Context scaling tab, see how token-generation throughput changes as the existing context grows, for the selected build, hardware, model, and quantization. 

What the numbers mean

The dashboard shows two separate tests, both measured in tokens per second:

Both tests start at context depth zero ( n_depth=0 ). PP512 measures processing 512 input tokens without generation; TG128 measures generating 128 tokens without a pre-existing context. The plotted value is the mean throughput ( avg_ts ). These are useful reference workloads, while the Context scaling tab lets you explore token generation throughput as the context grows. 

How we run the benchmarks

We benchmark the prebuilt binaries distributed through llama-install.sh , the build and installation project behind llama.app . The public gfx1151 and gfx1201 workflows are scheduled weekly and run the standard benchmarks using the llama-bench tool with Flash Attention on and off, with 10 repetitions per configuration. 

The model set evolves and currently includes Inkling 2 Mini, Qwen, Gemma, gpt-oss, and LFM models, covering both dense and mixture-of-experts architectures. Available GGUF formats include Q4_K_M , Q8_0 , other quantizations, and higher-precision formats such as BF16 and F16 . 

Inspect and reuse the results

The explorer reads directly from the public ggml-org/install.sh-benches-data Storage Bucket on Hugging Face. The data source link beside the chart title opens the folder for the selected build, hardware, and model. 

Standard results use <build>/<hardware>/<model>/<quant>.jsonl . Workload sweeps use the same folder <quant>-tg.jsonl filename. 

Use them to investigate a result, make your own charts, or compare with a local run.

We recently released NVIDIA Nemotron 3.5 Parse , a compact document model that turns page images into structured data for retrieval-augmented generation (RAG) and agents. 

Now we’re building on that release with synthetic training datasets, a fine-tuning recipe, and a DFlash2 speculator for faster inference . We’re also sharing how we trained Parse 3.5: first teaching document understanding through supervised fine-tuning, then using reinforcement learning to improve accuracy, consistency, and reliable completion. 

What Parse 3.5 produces

Parse extracts content from pages of documents into reading order, assigns content classes such as headings, paragraphs, tables, and charts, and returns bounding boxes that locate the content. Tables and charts become structured records that can power downstream document processing applications. 

Figure 1. Actual model output from a synthetic operations brief, showing the connection between the page and its structured representation. 

This latest version of Parse significantly extends its ability to read charts and tables, especially in more difficult and ambiguous cases. For example, bar charts or other plots that do not have any marked numeric values. The model is able to infer values by looking at the axes and height of the bar to derive these. Tables can be especially tricky because the structure is so meaningful, a shifted row or column can totally change the interpretation and meaning. These advancements have been largely powered by synthetic data generation, rendering variations of charts and tables with known ground truth and then training our model to reverse this process. 

We are open-sourcing three datasets used in the Parse 3.5 training : 

Synthetic Charts V1 — 9.98M examples : rendered charts and structured annotations for learning categories, series, and numerical values. 

Synthetic Tables V1 — 1M examples : rendered HTML tables with targets that preserve rows, columns, headers, and cell relationships. 

OCR Synthetic Multilingual v2 — 7.9M examples : synthetic document pages with Parse-format targets across varied fonts and layouts, for multilingual OCR and structured page reading. 

Each release includes images, annotations, generation documentation, and the training format. Use these pairs to fine-tune document models or create new variations for a target document type or language.

SFT teaches the capability; RLVR improves consistency

We trained Parse 3.5 with two phases of training. Supervised fine-tuning (SFT) spanning text, layout, tables, charts, and multilingual documents. Learning to predict structured targets established the general capability of reading a page and representing its contents. 

We then continued with reinforcement learning with verifiable rewards (RLVR) , using Group Relative Policy Optimization (GRPO) . Rewards check the quality of sampled extractions. For example, a chart extraction can earn a better reward for recovering the correct series and values, producing a usable structure, and finishing without repeatedly generating the same content. 

A difficult page can have several valid representations. These checks give the model flexibility to find a correct answer without prescribing one exact token sequence, while discouraging looping and unfinished output.

Part 1: Understanding swarms and training to communicate 

This is an aspirational blog series for aspirational readers. We (us, the community, you) want to build our own agent swarms because they're exciting, challenging, and increasingly capable. Furthermore, it would be extremely cool if we could train our own agents to work in a swarm. And exponentially cool if those swarms used small and affordable models. 

That's what we'll do in this series! Each blog post will include some context on building swarms, alongside reproducible examples that you can run on Hugging Face Jobs. This post's example takes about five hours on two H200s, which costs roughly $50. 

Multi-Agent Systems are hard to get working. Adding agents changes the agent's context, the budget, and in turn the complexity of the whole system. Mixing agents' context together through communication is not an inherent performance boost compared to a single agent. The model needs to learn to communicate through training. How do we define what models should learn? And which model weights do we update when we're dealing with many agents? 

In this series, we'll work through those problems with an educational overview and practical examples. Each post will introduce a question, build a small system, and examine what happens and how you can reproduce it. This first example starts with four agents, a shared language model, and a simple verifiable task. It's ideal to implement yourself, to tinker with, and to learn from. 

First, we'll start off with some context on swarms. 

The rise of the swarms

We've heard a lot about swarms over the past few months, both good and bad. In September this year, OpenAI announced that a swarm of roughly 10,000 agents had found a singularity in the 3D Navier-Stokes equations, one of the Millennium Prize problems. A smaller group of nearly 100 agents had already disproved regularity for the unforced 3D Euler equations, a closely related open problem. 

But swarms don't always work on the problems we want them to. Abstract: We propose a background independent quantization of vacuum general relativity on four dimensional Lorentzian spacetimes. Starting from first order gravity, we solve the gravitational constraints on intersecting null cones of a bulk subregion and obtain the reduced phase space at finite $G_N$. We promote its canonical Poisson brackets to commutation relations and use deformations of the reduced action to define an algebra of observables. ## 21. Proving a fixed upper bound on Jensen's affairs

- 出どころ: Hacker News（41 points / 6 comments）

### 本文(抜粋)

Proving a Fixed Upper Bound on Jensen's Affairs — bitbanter 

View this post as a beautifully rendered PDF instead: 2026-11-25-proving-a-fixed-upper-bound-on-jensens-affairs.pdf 

Abstract 

Recent AI-led advances in pure mathematics have solved most open problems, rendering further study there moot. But while there is still time, we can turn our attention to the most important problem of applied math today: finding a fixed upper bound on Jensen Huang&rsquo;s extramarital affairs. 

We derive a closed-form upper bound of \(A \le 22\,116\) under a dual-use time-allocation model that treats a substantial fraction of scheduled work hours as available for affairs with subordinates. The bound holds regardless of the precise start date of active pursuit (provided it is no earlier than the founding of Nvidia) and remains finite under modest concurrency. We conclude with an open invitation for lower-bound refinements. 

History of the Problem 

For years, Jensen Huang was widely regarded as one of the greatest entrepreneurs and leaders in modern history. But a select few knew that he was also an insatiable sex machine, that his partners outnumbered his leather jackets, and that his thirst for economic dominance paled in comparison to his unquenchable libido. 

This information asymmetry changed dramatically weeks ago, as revelations came to light that Huang had &mdash; at least &mdash; several affairs, including with suppliers (of dubious repute) and subordinates at Nvidia. But just how many? This paper posits that the true accounting is impossible to reckon, but it is possible to find an upper bound. 

The Assumptions 

Public reporting links Jensen to at least 3 affairs, which gives us a solid starting point. The following modeling assumptions are adopted: 

Each day is partitioned into sleep and non-sleep time. Sleep is bounded below by 6 h/day; the remaining ≤ 18 h are potentially available. 

Non-sleep time comprises both residual free time and scheduled work time. Work time is not excluded from the affair budget, because affairs with subordinates can (and, under the model, may) occur during working hours. 

An “affair” is defined as a distinct extramarital partner. Each new partner requires a minimum of \(h\) dedicated hours (drawn from the non-sleep pool) to initiate; subsequent maintenance is charged against the same pool but does not increase the count of distinct partners. 

Active pursuit of affairs is assumed to have begun no earlier than the founding of Nvidia (5 April 1993). Any later start only tightens the bound. 

Partners may be sequential or concurrent; the primary bound uses the sequential case. A concurrency robustness check is given later. 

The Calculation 

Let \(T\) be the number of days from 5 April 1993 to the present ( \(T = 12\,287\) as of 25 November 2026). Let \(a \le 18\) be the maximum non-sleep hours per day available for affairs (free time plus dual-use work time), and let \(h \ge 1\) be the minimum hours required to initiate a new partner. Then the total available-hour budget is \(B = T \cdot a\) , and the number of distinct affairs satisfies 

\[
A \le \left\lfloor \frac{B}{h} \right\rfloor = \left\lfloor \frac{T \cdot a}{h} \right\rfloor.
\] 
Under the conservative parameter choice \(a = 18\) , \(h = 10\) we obtain 

\[
A \le \left\lfloor \frac{12\,287 \cdot 18}{10} \right\rfloor = 22\,116.
\] 
 Robustness under concurrency. 

If up to \(c\) partners may be maintained simultaneously, each still consuming hours at rate \(r\) h/day, the initiation budget is reduced by the maintenance load. The resulting bound remains finite: 

\[
A \le \frac{T \cdot a}{h + c \cdot r \cdot \tau},
\] 
where \(\tau\) is the average duration (in days) of an affair. For any finite \(c,r,\tau\) the right-hand side is finite. Note that the dual-use treatment of work hours already expands \(a\) relative to a free-time-only model; concurrency does not reverse that expansion.
