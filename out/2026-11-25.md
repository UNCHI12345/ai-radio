The challenge isn’t the task—it’s the scale 

iFood maintains more than 15,000 code repositories. Each periodically needs specific tasks performed: validating code to ensure it meets internal standards, fixing vulnerable dependencies, or running an analysis. 

None of these tasks is difficult on its own. The challenge comes when those tasks multiply. 

“Solving this for one repository is easy. The challenge is solving it at scale,” says Victor Coelho, Senior Software Engineer at iFood. “The Remote Agents Platform is designed to make it possible to solve this at scale across all 15,000 repositories.” 

Before the platform, each team tackled the problem in its own way—and they all ran into the same obstacle. 

“Before, we had fragmented solutions. Imagine several teams at iFood trying to solve different problems, but without this layer, this agentic runtime, available to them. In the end, those solutions always ran into the same problem.” 

What was missing wasn’t intelligence or a use case. It was execution infrastructure. A dedicated runtime . 

“Teams can focus on solving their business problems and delegate execution to our platform.” 
—Victor Coelho, Senior Software Engineer, iFood 

A coding agent in the cloud, accessible through an API 

The team describes the Remote Agents Platform as an API that launches a remote agentic coding task. The cycle has three steps: the user submits a prompt and environment requirements through a REST call; the platform processes the task on a dedicated remote runner inside an isolated sandbox; and the result is retrieved later. 

“The platform’s entry point, its interface, is a simple REST API. Users can use this API to create the runs they need. Internally, we handle and manage the entire lifecycle and delegate execution to isolated sandboxes,” he explains. Task progress can be monitored in real time. 

The runner’s internal design alternates between two different types of steps—and that combination makes the overall workflow predictable. 

Deterministic steps bookend the workflow: cloning the repository, importing the skills the agent can use, and setting up the working branch at the start; publishing the merge request and making the generated artifacts available at the end. In between is the agentic execution itself, running GPT‑5.6 Luna inside the sandbox. 

“It’s a combination of those two things: deterministic steps and agentic execution within the workflow.” 

The sandbox runs Ubuntu and includes the toolchains iFood’s ecosystem requires—Python, Java, Kotlin, C#, TypeScript, Rust, JavaScript, and Go—along with general-purpose tools. Beyond the sandbox, the agent can access Nexus, GitLab, Docker, Snyk, Kubernetes, and AWS.

I gave a keynote at the AI Engineer Code Summit a couple of weeks ago, constructed around the idea that there have been three significant inflection points in the abilities of LLMs and coding agents in the past twelve months. 

Here's the video of the talk. In this post I'm going to pull out the major inflection point theme and interrogate it more deeply. 

Coding agents in November 2025 

Today, November 24th 2026, is the one year anniversary of the release of Claude Opus 4.5 . With hindsight, this was a consequential model. 

In the Opus 4.5 announcement, Anthropic said: 

Testers noted that Claude Opus 4.5 handles ambiguity and reasons about tradeoffs without hand-holding. They told us that, when pointed at a complex, multi-system bug, Opus 4.5 figures out the fix. They said that tasks that were near-impossible for Sonnet 4.5 just a few weeks ago are now within reach. 

This held up. 

Claude Code was 9 months old at that point, having been introduced alongside Claude 3.7 Sonnet on February 24th, 2025. 

Opus 4.5 was the first model I had used with Claude Code where the default result was generally the right thing. I hadn't been using Claude Code as a daily driver because it didn't feel reliable enough - I had to correct it often enough that it didn't feel like a clear accelerant. 

The new Opus changed that. For most of the coding problems I faced on a daily basis, Opus would get them right . It was clearly faster than working through the problems myself. 

Also in November, OpenAI released GPT-5.1 Instant, GPT-5.1 Thinking, GPT-5.1-Codex, and GPT-5.1-Codex-Max. These had a similar effect on their Codex coding agent: it became reliably useful for many of my coding tasks. 

The timing was convenient, because the December holidays were upon us. A lot of people, myself included, spent December tinkering with these new tools to see what they could do. By January we were ready to use them for our actual work. 

Fable class models in June/July 

We got our first hint of Claude Fable in April, when Anthropic announced Claude Mythos and said that it was too dangerous to release , due to its improved cybersecurity capabilities. Mythos was a model that could not just find security vulnerabilities, it could also figure out how to exploit them. 

In June we got to see how good that model was for ourselves, with the release of Claude Fable 5 - a defanged Mythos, that would solve most problems but would actively block you from using it for security work. 

After three glorious days... the US government took it away from us. Fable 5 was placed under export controls that effectively banned the model. We wouldn't get it back until July 1st.

Give it a goal, give it the right tools, and watch it cook.

These now represent the baseline for what I expect from a frontier model.

GPT 6.2 Astra Solves a Historical Mystery 
Here's an interesting case-study in using GPT-6.2 Astra for historical research, from history professor Mark Humphries: 

With only minimal prompting, GPT-6.2 Astra was able to autonomously identify the creator of an anonymous 1808 sketchbook held at Yale’s Beinecke Library . It did so extremely quickly (in just 22 minutes), using publicly available primary and secondary sources. To do so, it discovered a little known source in a paper archive, predicted that it would prove its hypothesis if examined and, in the end, it did. Not only that, but this new source turns out to be a major find on its own that will be of significant interest to both Canadian and fur trade historians. 

Here's the digitized sketchbook . 

Astra found a diary reference reference to a visit by the vicomte de Chabot dated five days before a date mentioned in the sketchbook at a nearby river, and suggested that Chabot's journal of his travels (only available by order from Cleveland State University) might confirm that the sketchbook was his work. 

Are historians due for a round of Deep Blue ? Mark thinks it will be mild: 

But if the experience of mathematics is any guide, we can also anticipate that sometime next spring or summer we’ll face a sort of crisis of confidence as we struggle to understand how to respond to agentic systems that can do things human historians cannot. To be fair, that crisis will almost certainly be less profound for us than it is for math. The problem in mathematics, of course, is that solving hard math problems was the whole game. Historians, on the other hand, constantly reinterpret the past in light of an evolving present; we don’t chase a single universal truth. We also (in the ideal at least) write books and articles that are closer to works of philosophy and literature than they are to scientific tracts. Humanity is thus something of a requirement for the production of historical literature.

Introduction

A walking policy can keep Microduck balanced, but it does not tell the robot how to steer around an obstacle in its path. In this workflow, we reuse the walking policy from our first Microduck tutorial and keep its weights fixed. This follow-up trains a separate avoidance controller using time-of-flight (ToF) sensing. You choose a direction with a gamepad; the controller adjusts the velocity command before passing it to the walking policy. 

NVIDIA Isaac Lab is an open-source framework for training policies across thousands of GPU-parallel simulations and it provides the robot-learning environment. Newton simulates physics and the sensor’s depth measurements. We will cover the control architecture, train on varied obstacle layouts, evaluate the resulting policies, and prepare the interface for hardware testing.

A configured Microduck. Load the same backlash walking-policy export used by the navigation task. 

A supported ToF sensor with its configuration recorded. 

A paired gamepad and a level test area with obstacles.

Last year Zach Wimpee and I trained a tiny GPT to write cursive . It worked but it only knew one hand (mine) and it learned from 3,500 words that I wrote on a trackpad. 

So here’s the obvious next question: can one small, ordinary transformer learn to hold a pen in lots of hands and draw as well as write? PenGPT is my attempt. There are two models. A 6M-parameter one writes print and cursive and picks up the handwriting of someone it has never seen from a few of their words. A 54M-parameter one draws from a text prompt. 

Then I took the thing apart to find out why it works. The answer wasn’t what I expected. 

How it works 

The whole recipe. Pen points snap to a grid (b) so a word becomes a walk in eight directions plus pen-down and pen-up. Byte-pair encoding merges common runs of moves into tokens (c): this "world" goes from 156 moves to 47 tokens. Everything else is a plain decoder that cross-attends to what it's told.

That’s it for the modality-specific part: ten symbols and a merge count. The same tokenizer handles handwriting and drawings. For handwriting the model is told the text; for drawings it’s told a SigLIP 2 vector so a typed phrase can stand in for a picture. 

The data 

Almost nobody records pen strokes so I made the handwriting data from scans: 495,590 words by 1,255 writers, mostly from two research collections plus old letters and diaries from public archives. A vision-language model finds legible pages and transcribes them, the pages get cut into words, InkSight traces each word back into strokes and a set of checks throws out bad traces. Between a third and a half of the words survive. 

The drawings are 477,670 sketches from ten public datasets. Quick, Draw! has 50 million and I kept the best 0.5%. I’m not releasing the datasets but the paper’s appendix explains how to build them.

Skip to content 

Philipp D. Dubach 

Contents Contents Key takeaways Token volume and token prices are moving at roughly the same speed, so cheaper inference on its own does not grow AI revenue. 

Token volume and token prices are moving at roughly the same speed, so cheaper inference on its own does not grow AI revenue. 
The price of a fixed level of capability collapses each year, while the cost of running frontier models rises; the revenue sits at the frontier. 
Closing the gap between capex and revenue needs money that today pays for labor, and outcome pricing is how vendors are reaching for it. 
The capex and cash flow figures from March have grown worse: five hyperscalers spent $560 billion in the first three quarters of 2026. 

In March I wrote that the hyperscalers&rsquo; answer to collapsing inference prices is Jevons: cheaper tokens create so much demand that total spending grows anyway. 
On volume, they look right. Google processed 9.7 trillion tokens a month in May 2024 . In May 2026 it was 3.2 quadrillion, 330 times as many. Amazon, Microsoft, Alphabet, Meta and Oracle spent $230 billion on capex in the third quarter of 2026 alone, almost four times what they spent two years earlier. 
But tokens aren&rsquo;t dollars. Revenue is price times volume, and the price is falling too. So my question is: does demand for tokens grow faster than the price of a token collapses? 
The arithmetic 
If the price of a token falls 10x and volume grows 10x, revenue is flat. Revenue only grows when volume grows faster than the price falls. 
Google&rsquo;s first-party model APIs went from 7 billion tokens a minute in Q3 2025 to nearly 32 billion in Q3 2026 , up 4.6x. Google&rsquo;s tokens across all products grew 6.7x between the I/O keynotes of 2025 and 2026. OpenRouter went from 0.5 trillion to 128 trillion tokens a week in 20 months , about 27x a year. On the price side, MIT researchers find that the price of reaching a fixed benchmark score falls 5 to 10x a year, and Epoch AI finds that cost per task at fixed performance falls about 13x a year. 

Volume and price move at about the same speed. That proves nothing by itself, because Google&rsquo;s tokens aren&rsquo;t sold at fixed-capability prices (like the ones Epoch measures). But it lines up with what Mert Demirer, Andrey Fradkin, Nadav Tadelis and Sida Peng found when they used OpenRouter and Azure data to estimate short-run price elasticities &ldquo;just above one&rdquo; and concluded that this leaves &ldquo;limited scope for Jevons-Paradox effects.&rdquo; At an elasticity of one, a 10x price cut buys 10x the tokens for the same money. 
That matches how a lot of buyers behave. Say a bank&rsquo;s head of operations has $2 million approved for AI contract review, and then the vendor cuts its token prices tenfold. The bank can now review ten times as many contracts, which is great. The budget still says $2 million. From CUDA and JAX to TorchTPU: Lessons from a Cayley Graph Solver 

Some time ago, I shared a blog post about working with Cayley graphs, where I solved combinatorial puzzles using AI coding agents, PyTorch on GPUs, and JAX on TPUs. Recently, Google released TorchTPU, a native PyTorch backend for TPUs, and I wanted to see how well it works on the same task: whether a PyTorch-native TPU stack could match my A100 training pipeline and my JAX beam search in speed and solution quality, or maybe even beat them. 

The short version: getting TorchTPU to work was easy; getting it to work efficiently was considerably harder. My initial training port was 1.65x slower than the A100 implementation, while the first TPU beam search was 5.7x slower than its JAX counterpart. 

After optimizing eager execution, rewriting attention, eliminating dynamic tensor shapes, fixing a subtle deduplication bug, and investigating an attention-routing regression, the results changed substantially. Training reached comparable wall-clock performance to the A100, and the optimized TorchTPU beam search became 25% faster per level than JAX on the same eight-chip v6e machine, producing the same total solution length across six test puzzles. 

Along the way, the investigation improved the solver itself and resulted in an upstream TorchTPU GitHub issue that led to attention-routing fixes.

The problem 

The CayleyPy Professor Tetraminx competition requires finding the shortest sequence of moves that solves 1000 scrambled puzzles. Formally, it is a shortest-path problem in a Cayley graph (each puzzle state is a node, and each of the 24 possible moves is an edge) with an 88-sticker state. 

My solver uses beam search guided by a learned neural heuristic — a 3.4M-parameter PieceTransformer . Instead of treating the 88 stickers individually, it groups them into 50 physical pieces, turns each piece into a token, adds a class token (51 tokens in total), and runs four small transformer layers with eight heads of size 32. At the end, an all-neighbours Q head (a head that predicts, for each of the 24 moves, the distance to solved after that move) outputs 24 numbers. So the beam scores all 24 children of a state with one forward pass on the parent. 

For training, the signal is a mix of cheap random walks and exact ground truth: 

Random walks of 2–40 moves from the solved state. A state p moves into a walk has two known labels: undoing the last move gives distance p - 1 , and continuing the walk gives p + 1 . 

Exact 24-way labels from a breadth-first search (BFS) table at depth 5 or less. 

The puzzle’s 24 spatial symmetries, used as data augmentation. 

On the A100, one epoch takes 142.7 seconds . My best checkpoint is epoch 1500 of a 2000-epoch run, about 80 hours in total. 

What is TorchTPU 

TorchTPU is not PyTorch/XLA : there is no LazyTensor tracing, no xm.mark_step() , and no xla_device() .
